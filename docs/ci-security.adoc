=== Required repository setup

The existing `debug-release` GitHub Environment has
required-release-maintainer approval and a deployment branch policy
permitting only `main`. Do not create, replace, or weaken that
environment as part of normal workflow changes. The publisher must be
dispatched from `main`; that branch restriction applies to the
publisher workflow definition, while its validated artifact may
originate from a pull request.

Production deployment jobs must continue to use protected environments.
Pull-request validation and untrusted debug-build jobs must not
reference a protected environment or receive its secrets.

=== Trusted workflow checkout provenance

Privileged `pull_request_target` and `workflow_run` jobs must not
pass a `github.event.pull_request.*` or
`github.event.workflow_run.*` expression to `actions/checkout`.
OpenSSF Scorecard reports every such form as `Dangerous-Workflow`,
even when a separate condition proves that the revision came from
protected `main`.

Trusted release workflows use the literal
`main` ref, then immediately compare the checked-out commit to
`github.event.workflow_run.head_sha` supplied through an environment
variable. The release job fails closed before GitVersion, builds,
registry login, tagging, or publication if protected `main` has
advanced or the completed upstream run does not match. Release checkouts
never persist credentials. The binary release job has job-level
`contents: write`, used to create the Git Data API tag after the build
and to publish the GitHub Release.

Pull requests use the `Lint and Test` workflow directly. If a ruleset or
branch protection rule still requires *Trusted workflow policy*, remove

Validate the transition in `Ensono-staging/eirctl-test` before changing
production rules. After the reporting workflow has produced a default-branch
coverage baseline and a successful PR upload, configure GitHub's Restrict

GitHub's coverage uploader does not support fork PRs, so this check cannot
guarantee coverage reporting for forks. Do not remove the existing SonarCloud
required check until the replacement checks and fork limitation have been
reviewed.

=== Ownership governance

`.github/CODEOWNERS` assigns `.github/CODEOWNERS` and executable
workflow files to
`@Ensono/digital-tools-maintainers`. The `main-is-main` ruleset must
require code-owner review for these files. CODEOWNERS is merge
governance only: it never authorizes runtime behavior and does not
replace workflow isolation, immutable provenance validation,
least-privilege permissions, or secret scoping.

=== Pull-request reporting

Pull-request source executes only in read-only jobs. The Go quality job
reports `govet` and `gocyclo` findings as SARIF; the test job generates
Cobertura coverage and JUnit reports. Separate jobs download those reports
without a source checkout and upload them with only the permissions needed
for code scanning, code quality, or test checks. The SARIF category for Go
quality is separate from Trivy and CodeQL.

The test job checks out the PR head for coverage line mapping. The coverage
upload is skipped for forks because GitHub does not grant their PR tokens
the required permission; a skipped upload is not a coverage result.
Because the SARIF upload jobs have no source checkout, GitHub may be unable
to calculate source fingerprints and may show duplicate alerts.

=== Debug prerelease process

==== Cache authority boundary

On June 26, 2026, GitHub introduced
https://github.blog/changelog/2026-06-26-read-only-actions-cache-for-untrusted-triggers/[read-only Actions cache access for untrusted triggers].
GitHub's current
https://docs.github.com/en/actions/using-workflows/caching-dependencies-to-speed-up-workflows#cache-access-for-low-trust-workflow-triggers[cache access documentation]
states that only default-branch `push`, `workflow_dispatch`,
`repository_dispatch`, `delete`, `registry_package`, `page_build`, and
`schedule` runs can create or overwrite caches in the default branch's
scope. Other default-branch-context events, including `issue_comment`,
receive read-only cache access when an untrusted actor can trigger them.
Ordinary `pull_request` caches remain scoped to the pull request merge
ref rather than the shared default branch.

A reusable workflow does not create a new root trust event. The
https://docs.github.com/en/actions/sharing-automations/reusing-workflows[caller invokes it as a job],
and its permissions can only be maintained or reduced. The debug builder
therefore inherits the authorized request run's effective
`issue_comment` event and read-only default-branch cache boundary. A
`workflow_dispatch`, `repository_dispatch`, default-branch `push`, or
other documented cache-writing event must not call the builder even if the called
workflow declares `contents: read`, disables checkout credentials, and
sets `setup-go` caching to `false`. Disabling convenience caching is
defense in depth; pull-request code can otherwise address the cache
service directly.

The debug prerelease process has four separate trust domains:

[listing]
....
maintainer /build-debug comment
            |
            v
trusted issue_comment authorization (no checkout)
            |
            v
local workflow_call builder (read-only cache, untrusted execution)
            |
            v
fresh trusted finalizer (bounded opaque files + provenance)
            |
            v
main-only validator --> protected debug-release publisher
....

[arabic]
. *Trusted authorization:* an exact `/build-debug` comment on a pull
request starts *Request debug build*. A checkout-free job accepts only
commenters with repository `write`, `maintain`, or `admin` permission,
requires this repository as the open pull request's base, captures the
current full head SHA, and emits only the PR number and SHA.
. *Untrusted reusable builder:* a dependent job calls the local *Debug
build* `workflow_call`-only workflow with those typed required values.
The builder re-reads the pull request immediately before checkout and
fails if the head moved. It checks out only that exact SHA with
`contents: read` and `persist-credentials: false` on a GitHub-hosted
runner, receives no secret or environment, disables automatic Go
caching, and uploads only a run-and-attempt-specific intermediate
binary artifact.
. *Trusted finalizer:* a fresh GitHub-hosted job revalidates the PR and
SHA, downloads the intermediate artifact without executing it, and
requires the exact seven expected regular binary files within reviewed
per-file and aggregate size bounds. Symlinks, special files, missing or
extra files, unsafe layout, and empty or oversized binaries fail the
run. The clean job creates provenance from trusted authorization and
run metadata and uploads the immutable final
`debug-build-<run-id>` artifact. An attacker-created final-name
collision causes the trusted upload and request run to fail rather than
making the artifact eligible.
. *Trusted publisher:* a maintainer dispatches *Publish debug
prerelease* from `main` with the request run ID, pull-request number,
and full commit SHA. Both jobs fail closed on another ref. Read-only
validation accepts exactly one unexpired final artifact from a
successful `.github/workflows/debug-build-request.yml` run whose root
event is `issue_comment`, rechecks the current PR head, and verifies
repository, event, workflow path, PR, SHA, run ID, run attempt, artifact
name, finalizer identity, and provenance. Only then can the separate
`debug-release` environment-gated job receive `contents: write`; it
redownloads only the validated artifact ID, repeats provenance checks,
and passes the seven explicit binary paths to the pinned release
action.

==== Operator procedure and rollback

[arabic]
. Confirm the intended pull request is open and its current head is the
revision to build.
. As a maintainer, comment exactly `/build-debug`; edited text,
additional arguments, unauthorized actors, and issue comments that are
not attached to a pull request do not call the builder.
. Record the resulting *Request debug build* run ID, run attempt, full
head SHA, intermediate artifact name, and final
`debug-build-<run-id>` artifact. A newer PR head requires a new comment;
do not reuse a stale run.
. To publish, dispatch *Publish debug prerelease* from `main` with that
request run ID, PR number, and full SHA. Treat validation success as
artifact identity evidence, not as trust in the binary contents. Normal
`debug-release` approval remains required.
. After testing, remove draft/test release state when applicable and
allow the intermediate one-day and final fourteen-day artifact
retention policies to clean up, or delete test artifacts through the
approved repository process.

Cache contents are not signed and must never contain credentials or
other sensitive data. The read-only boundary depends on GitHub.com's
documented service policy and on reusable jobs retaining the caller's
effective root event. If GitHub changes that policy, CodeQL classifies
the topology as cache-write-capable, a new high-severity workflow alert
appears, or live validation does not show the expected event and
artifacts, disable the request/build call. Do not roll back to direct
`workflow_dispatch` execution or to `GITHUB_TOKEN` label mutation:
the former restores default-branch cache-write authority and the latter
is suppressed from starting the labeled workflow. Retain the protected
publisher while the request path is disabled.

Repeated authorized requests remain serialized per PR without
cancelling an already-running immutable build. Trusted jobs download
artifacts as opaque data and never source, install, execute, or add them
to the command environment. Published releases identify the PR and
immutable source SHA; consumers must treat every binary as untrusted
debug output.

=== SSH server trust

Git-over-SSH verifies server identity by default using ordered
`UserKnownHostsFile` and `GlobalKnownHostsFile` selections from SSH
configuration or supported `GIT_SSH_COMMAND -o ...` options. Quote or
escape a path containing spaces (for example,
`-o UserKnownHostsFile="~/.ssh/team known_hosts"`); repeated
directives and multiple configured files retain their order. If no
custom file is selected, readable `~/.ssh/known_hosts`,
`~/.ssh/known_hosts2`, and platform defaults are used:
`/etc/ssh/ssh_known_hosts{,2}` on Unix and
`%ProgramData%\\ssh\\ssh_known_hosts` on Windows. SSH aliases and
ports are resolved before connection; non-default ports require the
OpenSSH `[host]:port` known-host form.

Provision a host key before using a Git import, for example by obtaining
and reviewing it through the repository owner's documented channel
before adding it to `known_hosts`. An unknown host or changed host key
stops the connection; verify the host identity out-of-band, remove only
the obsolete entry, and add the reviewed replacement key. Errors
intentionally identify only the host and remediation, never private
keys, passphrases, or tokens.

`StrictHostKeyChecking=no` in the selected SSH configuration or
supported `GIT_SSH_COMMAND -o` option is a temporary compatibility
escape hatch. It disables server verification and emits a warning on
every connection; use it only while provisioning a verified known-host
entry, then remove it.

When updating maintained CI contexts or tools, update the readable tag
and reviewed digest together, record the manifest evidence above, and
run `scripts/check-immutable-ci-dependencies.sh`. The check rejects
tag-only task-runner images, floating GitVersion selectors, and
`govulncheck@latest`.
